## 3. 差异分析：不是难样本，是量化敏感

我把那 7 张喂给 **float 模型**看置信度，结论很清楚：

| 样本 | float 判决 | **float 的 left 概率** | → **int8 的 left 概率** |
|---|---|---|---|
| 0117 | left | **1.000** | **0.375** |
| 0132 | left | 0.949 | **0.027** |
| 0150 | left | **1.000** | **0.154** |
| 0168 | left | **1.000** | **0.072** |
| 0174 | left | 0.988 | **0.008** |
| 0178 | left | **1.000** | **0.232** |
| 0180 | left | 0.828 | **0.000** |
| **对照 5 张（两边都判对）** | left | 1.000 | **1.000** ✅ |

**float 对这 7 张几乎全是 100% 自信，量化后 left 概率直接塌到 0~37%。**
而对照组量化前后都是 1.000，**完全无损**。

**所以这不是"难样本被量化推过界"，而是"这 7 张本身对量化敏感"。**

### 那 7 张有什么共性？

```
dx:  87.1  87.1  90.3  93.5  91.9  90.3  91.9
left 全类 dx 分位： P25 = 94   中位 = 98
```

**全部落在 dx 最小的那个四分位** —— 即**距离较远、crop 较小**（174×63 ~ 187×68）的样本。
crop 小意味着放大到 128×64 时细节本来就被插值糊过一轮，量化的微小损失更容易把它推过界。

**这与你们的 1 张并不矛盾**：`left_0180` 在两个环境里都失败，说明它最敏感；
其余 6 张处在边界上，不同的 QDQ 实现给出不同结果。**两边都是真实测量，不是谁报错了。**

## 4. 放行决定与理由

**放行。** 理由：

1. **三项验收取较差侧仍全部达标**（left 0.964 vs 线 0.85）
2. **板端是 ATON NPU 的独立实现，既不是 ORT 也不是 PyTorch** ——
   它可能比 ORT 好（像你们那版），也可能更差。**PC 端两个结果都只是参考，最终以板端实测为准。**
3. **重新量化的收益不确定**：QOperator 路线已被工具链封死（`Unsupported layer types: QGemm`），
   只剩调 calib 数量这一个旋钮，收益有限且要重跑一轮。
4. **有一个已知的针对性场景可以验证**（§5.2），板端测完就知道要不要回头。

**如果板端"远距离左看"明显不行，再回头重新量化** —— 那时有明确靶子，比现在盲调有效。

### 5.3 ⚠️ 最关键：量化常量的传递

**这是最容易出事的一环。** 板端 `eye_cam_main.c` 里硬编码了四个常量，
用来把相机像素转成 int8 张量、以及把裸输出还原成 logits。
**它们必须和 stedgeai 实际使用的值一致，否则每次推理都静默出错，不报任何异常。**

**我从 v3 的 ONNX 里读出来的值**（供你们和自己生成的 `network.c` 交叉核对）：

| 常量 | **v3 的值** | v2 时代板端的值 | 变化 |
|---|---|---|---|
| **input scale** | **0.0070742024** | 0.007135717 | −0.86% |
| **input zero_point** | **−14** | −13 | −1 |
| **output scale** | **0.17015758** | 0.129406050 | **+31.5%** ⚠️ |
| **output zero_point** | **−34** | −38 | +4 |

**`output_scale` 变了近三分之一** —— 板端若不更新，logits 数值会整体偏移，
虽然 argmax 不变（同比例缩放不改变 softmax 的排序），但**置信度显示会全错**。

**请你们从生成的 `network.c` 里把实际使用的这四个值提取出来，和上表逐项核对后一起回传。**
若有出入，以上表（ONNX 源头）为准排查——通常意味着 stedgeai 做了额外的转换。
